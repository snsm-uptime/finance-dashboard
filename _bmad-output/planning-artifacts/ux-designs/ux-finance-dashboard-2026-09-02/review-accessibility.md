# Accessibility Review — docs-tutorials-page

## Overall verdict

The spine pair gets the fundamentals largely right — the help icon has a real `aria-label` (not tooltip-only), the accordion is specified as `aria-expanded`/`aria-controls` real buttons, and illustrations are correctly marked decorative. However, the deep-link flow (hash → auto-expand → "scroll into view") is under-specified on focus management and leans on a **color-only, time-limited fade** as the sole non-visual-scroll orientation cue, which puts keyboard and screen-reader users at a real disadvantage relative to sighted mouse users. There's also no `prefers-reduced-motion` carve-out for the new chevron/fade animations, despite the base spine establishing Reduce Motion as a product commitment elsewhere. These are fixable with spine edits, not implementation-only patches — several are ambiguous enough that two implementers could reasonably build materially different (and materially less accessible) experiences from the current text.

## Findings

- **critical** Deep-link auto-expand only specifies "scrolls the target entry into view" (EXPERIENCE.md:22, "State Patterns" line 49) with no focus-management instruction. If the target `doc-entry` is not itself a focusable element (nothing in the spine gives it a `tabindex`/heading landmark that receives focus), a screen-reader or keyboard user who arrives via the help-icon deep-link gets **no equivalent orientation cue** to the sighted "scroll + 1s color fade" — they land at page top (default browser/Next.js navigation focus) and must serially navigate past the auto-expanded section with no indication anything already responded to their click. *Fix:* add an explicit rule: on hash arrival, move DOM focus to the target entry's heading (`tabindex="-1"`, `.focus()` on mount) and/or programmatically announce via a visually-hidden live region ("Showing: {entry title}"), matching the sighted user's implicit "you're now here" signal.

- **high** The only specified cue that a deep-linked entry is the target is color: "brief focus highlight (reuses `{finance-helper.colors.accent}` at low opacity as a 1s fade, no new color token needed)" (EXPERIENCE.md:49). This is a color-only signal (WCAG 1.4.1) with no accompanying shape/border/icon change, and a 1-second fade is easy to miss for low-vision users or anyone whose eyes are still on the URL bar/back button when the page settles. *Fix:* pair the fade with a non-color cue (e.g., a left border/outline that persists until next interaction, or an outline that matches the existing keyboard focus ring style) and extend/de-couple the duration from a hard 1s timeout — e.g., persist until scroll or next focus change, not a fixed animation.

- **high** No `prefers-reduced-motion` handling specified for the new chevron rotation (DESIGN.md:72) or the deep-link fade highlight (EXPERIENCE.md:49), despite the base finance-helper spine explicitly carrying a Reduce Motion commitment for other animated UI (EXPERIENCE.md base, Upload button: "Reduce Motion: spinner may be static; busy name still announced"). Given the fade is also the *primary* orientation mechanism per the finding above, a reduced-motion user could lose it entirely with no fallback specified. *Fix:* add a line to the Accessibility Floor section stating chevron rotation and the fade highlight respect `prefers-reduced-motion` (snap instead of animate) and that the fade is never the sole cue (ties to the high-severity color-only finding).

- **medium** `help-icon-button`'s focus-visible treatment is unspecified. DESIGN.md defines rest/hover color (`{colors.help-icon}` → `{colors.help-icon-hover}`) but the Accessibility Floor in EXPERIENCE.md only calls out "existing focus ring" for accordion headers (EXPERIENCE.md:50), not for the new icon-only button. Icon-only buttons on a transparent background are exactly the case where focus-ring contrast most often gets missed in implementation. *Fix:* explicitly state help-icon-button uses the same app-standard focus ring/outline as other interactive controls, and note it must meet 3:1 non-text contrast (WCAG 1.4.11) against both the page background and the icon's own transparent-background hover fill.

- **medium** Touch target size is unspecified in behavioral terms (only visual: `size: 2.25rem` = 36px, DESIGN.md:58, which does clear the WCAG 2.2 SC 2.5.8 24×24px CSS-pixel floor as drawn). But nothing constrains implementation from placing it flush against other header trailing-slot content (page title, other icons) with insufficient spacing, which SC 2.5.8 also implicates when targets are adjacent. *Fix:* add a minimum spacing/hit-area note (e.g., "no adjacent interactive element within Xpx") to the help-icon-button component spec, or explicitly note the 36px box already includes adequate padding beyond the visual glyph.

- **low** Decorative illustration handling is specified correctly (`aria-hidden`, "restate the adjacent text, not new information," mirrors `FeatureCard` treatment — EXPERIENCE.md:63) and is low risk as written. The residual risk is content-governance, not spec: if a future doc-entry illustration ever encodes information not present in the adjacent prose (e.g., a flow diagram with branches/labels that aren't fully restated in text), `aria-hidden` would become a genuine information-hiding failure (WCAG 1.1.1). *Fix:* add a one-line authoring rule to the Do's/Don'ts ("illustrations may never be the sole carrier of any step/branch not already in the body or step list text") so future entries don't drift into this trap without touching the spine again.

- **low** Deep-link affordance underline behavior — "underline: none, hover-underline" (DESIGN.md:96-97) — relies on color (`{colors.deep-link-text}`) plus a trailing chevron icon to distinguish the link from body text at rest, which is acceptable since it's a standalone block-level affordance rather than an inline text link (WCAG 1.4.1 applies most strictly to links embedded within a text block). No fix required, but worth confirming in implementation review that the deep-link is never rendered inline within `entry-body` prose, only as its own row/element as currently described ("at the bottom of the entry").

- **low** Multiple-sections-open accordion behavior (EXPERIENCE.md:43, "one open section at a time is not enforced") is good for cognitive load but the spine doesn't say whether `aria-controls`/`aria-expanded` region visibility is also reflected via `hidden` attribute vs. CSS-only collapse — a common implementation pitfall where AT still finds collapsed content in the accessibility tree. *Fix:* add one clause confirming collapsed accordion panels are removed from the accessibility tree (native `hidden` or `aria-hidden` synced to `aria-expanded`), not just visually collapsed.
