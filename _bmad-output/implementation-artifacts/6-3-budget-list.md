# Story 6.3: Budget list

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the only member of a list,
I want a Budgets tab with named caps,
so that I can see which envelopes are near their cap.

## Acceptance Criteria

1. **Given** a solo list (`member_count === 1`) **When** I open the Budgets surface for that list **Then** I can create a budget with **name**, **cap** (a positive money amount), and **currency** (FR-48), and I can see the list of budgets I've already created for that list.
2. **Given** a budget on that list **When** it is rendered in the list **Then** its **near-cap state** is visible (a distinct visual/text treatment once `spent / cap` crosses a threshold, separate from the plain "under cap" state) — **not** a bare percentage number with no state distinction.
3. **Given** this story lands **before** Story 6.5 (attribution) **When** budgets are listed **Then** every budget's `spent` is `0` (no ledger lines are attributed to any budget yet) — near-cap logic must exist and be exercised by tests, but will not visually trigger on real data until 6.5 ships. Do not fake a nonzero `spent` to make the near-cap state "look done."
4. **Given** `member_count ≥ 2` on a list **When** that list's detail is opened **Then** budgets are **not** the primary UI — the existing shared-settle chrome from Epic 5 renders unchanged, and no Budgets entry point is shown (FR-48, FR-50).
5. **Given** a non-member of a list **When** they call the budgets **read** endpoint for that list **Then** they get 404 `not_found`; **When** they call the budgets **create** endpoint for that list **Then** they get 403 `not_list_member` — consistent with every other list-scoped route's read-hidden-as-404 / mutation-deny-as-403 split (AD-19, `deny_as_not_found_for_action`).
6. **Given** CI **When** budget name/cap/currency validation and near-cap classification are tested **Then** domain unit tests cover: blank/too-long name, non-positive cap, cap with too many decimal places for its currency, unsupported currency, and the near-cap boundary (just under / at / just over the threshold) using `Decimal` — never `float`.

## Dev Notes

- **This is new persisted domain, unlike Stories 6.1/6.2.** 6.1 was UI-only chrome branching; 6.2 derived everything from already-committed `ledger_entries` with zero new schema. This story is the first Epic 6 story to add a table (`budgets`) and a repository. Follow the `cards` table/`CardRepository`/`api/api/routes/cards.py` triad as the closest structural precedent throughout (list-scoped-but-independent entity with its own CRUD), not the `spend_by_origin` read-model precedent from 6.2.
- **`spent` is always `0` in this story — this is correct, not incomplete.** Story 6.5 ("Budget attribution — manual and rules") is what adds `ledger_entries.budget_id` (or an attribution join table) and makes `spent` a real aggregate. Story 6.4's epics text says explicitly "history may be empty until Story 6.5 attributes lines" — the same logic applies here to `spent`/near-cap. Do not build any ledger-scanning/aggregation code in this story to make `spent` "look real"; `ListBudgetsService` hardcodes `Decimal("0")` and that is the full extent of this story's `spent` behavior. The near-cap **classification function** must still be fully unit-tested with synthetic `spent` values (Task 1) even though production data never exercises anything but `"ok"` yet — that is how AC #2's "near-cap state is visible" mechanism gets verified without waiting for 6.5.
- **The 90%-of-cap near-cap threshold is this story's invention, not a spec citation.** Checked PRD FR-48/FR-49, epics.md Stories 6.3/6.4, ARCHITECTURE-SPINE AD-29, and the sprint-change-proposal — none define a numeric near-cap threshold, only that "near-cap state is visible." `NEAR_CAP_RATIO = Decimal("0.9")` in `api/domain/budgets.py` is a documented judgment call (module-level named constant, not a magic number) so a future story or reviewer can change it in one place if product specifies a different number later.
- **No existing in-page tab pattern to reuse for "Budgets tab."** `TabBar.tsx` is the fixed global Home/Upload/Account bottom nav (DESIGN.md `components.tab-bar`) — structurally unrelated to a per-list "Budgets" tab. This story ships Budgets as its own route (`/lists/[listId]/budgets`) rather than inventing a new in-page client-tab component with no design precedent; see Task 5's inline rationale. Story 6.4 (budget detail) being a separate page too confirms this is the right shape for both stories, not just this one.
- **New ACL actions, not a reuse of `write_ledger`/`edit_default_split`.** Budgets are a distinct capability from ledger writes or default-split edits. Add `read_budgets` (member-read class) and `write_budgets` (member-mutation class) to `domain/list_access.py`'s action vocabulary — any member (not owner-only) can manage budgets on a list they belong to, matching FR-48's "the only member" framing (a solo list's one member is never distinguished as "owner" vs "member" in the UX for this feature).
- **Do not gate the budgets endpoints on `member_count == 1` server-side** — same AD-29 principle as 6.2's origin-spend endpoint: the API serves any list a member can read/write; the UI (Task 5) is solely responsible for showing/hiding the Budgets entry point based on live `members.length`. This keeps the "mode is live membership count, not a list type" invariant in exactly one place (the UI), consistent with `showSettleChromeFrom`.
- **Currency scope is CRC + USD only, matching this codebase's FX scope everywhere else.** `MaterializeFxService`/BCCR integration is v1-scoped to USD+CRC (project-context: "v1 is USD+CRC only"); a budget in a third currency would have no FX story if this codebase ever needs to reconcile budget currency against ledger CRC in Story 6.5. Reject anything else at validation (`validate_budget_currency`), don't accept an arbitrary ISO 4217 code just because `canonical_line.py`'s regex would.
- **Money discipline applies exactly as everywhere else.** `cap`/`spent` are `Decimal` server-side, `NUMERIC` in Postgres, and wire-serialized as strings (`format(value, "f")`) — never `float`, never a JSON number.
