# Story 6.5: Budget attribution — manual and rules

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the only member of a list,
I want to assign transactions to budgets by hand and by rules,
so that budget history and near-cap are based on real spend.

## Acceptance Criteria

1. **Given** a budget on a solo list (`member_count === 1`) and a committed, spend-included ledger line on that same list that is not yet attributed to any budget **When** I manually assign that line to the budget (from the budget's detail page) **Then** the line appears in that budget's transaction history and its `spent` total includes the line's amount (FR-49).
2. **Given** a ledger line already manually assigned to budget A **When** I assign it to budget B **Then** it moves — it appears in B's history/`spent` and no longer appears in A's (a line belongs to at most one budget at a time; assignment is a move, not an add).
3. **Given** a line manually assigned to a budget **When** I unassign it from the budget's detail page **Then** it no longer counts toward that budget's history/`spent`, and it becomes available again as an unassigned candidate (for manual assignment or rule matching).
4. **Given** a matching rule on a budget (a case-insensitive substring against the line's description) **When** an existing committed line's description matches and that line is not already manually assigned to a *different* budget **Then** the line is attributed to the rule's budget automatically — no second manual step, and this applies retroactively to lines that existed before the rule was created (FR-49).
5. **Given** that same rule **When** a new line is committed later (manual expense entry or import commit) and its description matches **Then** it is attributed to the rule's budget the next time that budget is viewed — attribution here is computed at read time from the rule text, not written by the commit path, so no changes are needed to import/manual-expense commit code for this to work.
6. **Given** a line that is *manually* assigned to budget A **When** a rule on budget B would also match its description **Then** the line stays attributed to A only — manual assignment always wins over a rule match; a line is never attributed to two budgets at once.
7. **Given** a budget's rules **When** I add or remove a rule from the budget's detail page **Then** the rules list updates, and history/`spent` are recomputed accordingly (no explicit "re-run rules" step required, per AC #4/#5's read-time computation).
8. **Given** a budget whose `currency` is `USD` **When** its detail or list-row `spent`/history is computed **Then** `spent` stays hardcoded to `0` and `history` stays `[]`, exactly like every budget did before this story — attribution/`spent` in this story is **CRC-only** (see Dev Notes for why); creating/editing a USD budget is otherwise unaffected.
9. **Given** committed lines whose `line_type` is outside the spend-included set (e.g. a non-purchase/non-reversal line) **When** attribution and candidate-picking are computed **Then** those lines are never offered as assignment candidates and never match a rule — same `INCLUDED_LINE_TYPES` filter `domain.settle`/`domain.spend_by_origin` already use (consistency with FR-45's "included lines follow spend" spirit).
10. **Given** a non-member of a list **When** they call any of this story's new budget-attribution endpoints (assign, unassign, list candidates, create rule, delete rule) for that list **Then** they get the same hidden-as-404 (read: `list_not_found`) / deny-as-403 (write: `not_list_member`) split every other list-scoped mutation/read already uses (AD-19) — no new ACL action; all of this story's endpoints reuse `read_budgets`/`write_budgets` from Story 6.3.
11. **Given** a budget id, ledger-entry id, or rule id that does not exist, or exists but belongs to a different list/budget than the URL **When** any of this story's endpoints are called **Then** the caller gets 404 with a distinct `code` per resource (`budget_not_found` — reused from 6.4; new `ledger_entry_not_found`, `budget_rule_not_found`), never a generic 404, and never leaked via a different status/shape than an equivalent nonexistent id.
12. **Given** an empty or whitespace-only rule `match_text`, or one over 100 characters **When** a rule is created **Then** it is rejected 422 `invalid_budget_rule_match_text` — same validate-then-persist discipline as budget name/cap/currency (Story 6.3).
13. **Given** `member_count ≥ 2` on a list **When** that list's budgets/attribution endpoints are called directly **Then** nothing changes from Stories 6.3/6.4's posture — the API is not gated on member count (AD-29); only the UI entry points stay solo-only.
14. **Given** this story **When** scope is considered **Then** loans and shared-list budgets are out (epics.md), and no changes are made to the import-commit or manual-expense-create pipelines (attribution is entirely a read-time computation over already-committed lines, per AC #5).
15. **Given** CI **When** attribution is tested **Then**: domain unit tests cover rule-match case-insensitivity/substring semantics, manual-wins-over-rule precedence, the CRC-only `spent` computation, and the `INCLUDED_LINE_TYPES` filter; API integration tests cover manual assign, re-assign (move), unassign, rule create + retroactive match on an existing line, rule create + match on a line committed afterward, manual-wins-over-rule, a USD budget staying at `spent: 0`/`history: []`, and the three new 404 code paths; a UI test covers defensive-parsing of the now-structured `history`/`rules` response shapes.

## Dev Notes

- **Attribution is computed at read time, not written at commit time.** A ledger line's `budget_id` column is the only *persisted* attribution signal (set by manual assign, cleared by unassign). Rule matches are **never** written back to `ledger_entries.budget_id` — `GetBudgetDetailService`/`ListBudgetsService` compute the rule-matched set fresh on every read by scanning the list's ledger entries against the budget's `budget_rules.match_text` rows (Task 1's `compute_attributed_entries`). This is a deliberate design choice, not an oversight: epics AC "new or existing lines match... without a second manual step" is satisfied because *any* read after the rule exists (or after the line is committed) sees the match — there is no batch job, no trigger, and critically **no change needed to the import-commit or manual-expense-create pipelines** (AC #5, #14). The tradeoff is that attribution is `O(list's ledger entries × list's rules)` per read rather than O(1); for this codebase's data volumes (personal/household finance, not a ledger with millions of rows) this is the right tradeoff — do not "optimize" this into a materialized/cached table without a measured need, per project-context's "don't add Redis/workers/a fourth service unless a measured NFR forces it" spirit.
- **Manual assignment always wins over a rule match, and a line belongs to at most one budget.** `compute_attributed_entries`'s `entry.budget_id is None` guard is the entire mechanism (Task 1) — a manually assigned line (non-null `budget_id`, whether it points at *this* budget or another) is never re-captured by a rule scan. This is what makes AC #2 (assigning to a different budget "moves" it) and AC #6 (manual wins) both true from one column + one guard, with no separate "assignment history" or priority table needed.
- **Why `spent`/`history` are CRC-only in this story (AC #8), even though `SUPPORTED_BUDGET_CURRENCIES` allows `USD`:** `domain.budgets`'s own comment (added in Story 6.3) already flagged this — "a budget in any other currency would have no FX story if 6.5 ever needs to reconcile it against ledger CRC." `ledger_entries.amount_crc` is the only materialized, already-converted total this codebase has (FX is materialized **at commit**, per AD-7/project-context — "FX at commit (BCCR) → materialize CRC fields; no FX override"). Computing a USD budget's spend would require converting `amount_crc` back to USD at *read* time using some rate — which contradicts AD-7's commit-time-only FX materialization, would need a live or cached BCCR lookup exactly where project-context says "never live BCCR in CI," and isn't specified anywhere (PRD, epics, ARCHITECTURE-SPINE, EXPERIENCE.md — checked all four; none mention a budget-currency-conversion story). Keeping USD budgets at `spent: 0`/`history: []` (identical to every budget's behavior before this story) is the honest, minimal choice; manual assignment and rule creation still work normally on a USD budget (Task 4 explicitly does not currency-gate those, only the spend/history *computation*) so nothing is silently lost if/when a future story adds the FX reconciliation — it only has to change the read path, not re-teach users a different assignment flow.
- **Money discipline, as always:** `amount_crc` on both `BudgetHistoryLineResponse` and `BudgetCandidateResponse` is wire-serialized via `format(value, "f")`, never `str(Decimal)`, never a JSON number.
- **Reuse, don't reinvent:** `INCLUDED_LINE_TYPES` (from `domain.settle`, already reused by `domain.spend_by_origin`) is the third consumer of this same purchase/reversal filter — do not define a fourth, budget-specific version of "what counts as spend." The `(id, list_id)`/`(id, budget_id)` two-column-`WHERE` not-found-vs-wrong-parent trick is reused three more times this story (`get_ledger_entry`, `get_rule`) exactly as `get_budget` established it in 6.4 — don't fetch-then-compare-in-Python anywhere in this story.
- **Scope discipline:** this story does not touch `api/application/expenses.py`'s commit path, `api/application/import_*.py`, or any import-pipeline file beyond the one-line `LedgerEntryRecord.budget_id` field addition and the `_ledger_entry_record()` mapper update (both needed purely so the *read* side can see the column — neither writes it). If implementation pressure suggests "just set `budget_id` at commit time to save a rule-scan," that's scope creep against AC #5's explicit "no second manual step... via a read, not a write" design — resist it.
- **Previous stories' pattern reminders (still apply):** ACL is `read_budgets`/`write_budgets` only, reused everywhere in this story — no new action. Hidden-as-404 for reads (`ListNotFoundError`), deny-as-403 for mutations (`NotListMemberError`) — same split every list-scoped route uses (AD-19). `member_count` is never checked by the API (AD-29) — only UI entry points are solo-gated, and this story adds no *new* entry-point gating logic (the budget detail page is already reached only via the already-gated budgets list page, per 6.3/6.4).

Key design decisions made and documented as judgment calls (no spec cites a mechanism for either): (1) attribution is computed at **read time** from a persisted `ledger_entries.budget_id` (manual) plus a scan against `budget_rules.match_text` (rule) — no write-path/commit-pipeline changes needed, satisfying "new lines match without a second manual step" via "any read after the fact sees the match"; (2) manual assignment always wins over a rule match via one `budget_id IS NULL` guard, so a line belongs to at most one budget; (3) `spent`/`history` computation is scoped to **CRC-only** budgets this story — a `USD` budget keeps the pre-6.5 hardcoded `spent: 0`/`history: []` behavior, because materializing `amount_crc` back into USD at read time would contradict AD-7's commit-time-only FX materialization and this codebase's "never live BCCR" rule; assignment/rules still function normally on USD budgets, only the spend computation is gated. Manual-assign UI is scoped entirely inside the budget detail page's own candidate picker (not the shared list-detail receipt-row menu) to keep this story's blast radius inside the budgets module and avoid touching UI shared with Epic 5's settle chrome.
