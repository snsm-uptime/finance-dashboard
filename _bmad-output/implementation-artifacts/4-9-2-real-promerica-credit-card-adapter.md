# Story 4.9.2: Real Promerica credit-card adapter

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer extending statement import beyond the Promerica stub,
I want a real `PromericaAdapter` that parses real Promerica credit-card statements into `CanonicalLine` rows,
so that Promerica uploads stop routing through the deliberately-fake stub (Story 4.5, FR-36) and parse for real, now that a real sample exists (`bank_data/PROMERICA_CRED.pdf`).

## Acceptance Criteria

1. **Given** a real Promerica statement (`PROMERICA_CRED.pdf`), **when** `PromericaAdapter`'s content sniff runs, **then** it detects the statement via a marker unique to real Promerica statements (e.g. "Banco Promerica de Costa Rica" + "MOVIMIENTOS DE LA TARJETA DE CRÉDITO") — replacing the stub's deliberately-fake `ESTADO DE CUENTA PROMERICA STUB` marker (Story 4.5).
2. **Given** `PromericaAdapter`'s declared `_SECTIONS`, **when** compared against real printed section titles, **then** the title strings match real headers exactly as printed — "Detalle de pagos del periodo" (PAYMENT, MUST_PARSE), "Detalle de compras del periodo" (PURCHASE, MUST_PARSE), "Detalle de intereses" (INTEREST, MUST_PARSE), "Detalle de otros cargos" (FEE, MUST_PARSE), "Detalle de productos y servicios de elección voluntaria*" (VOLUNTARY_SERVICE, BEST_EFFORT), "Cargos por gestión evidenciable de cobro**" (IGNORE) — mirroring Story 4.9's real-header-matching fix for BAC credit, not invented text.
3. **Given** `PromericaAdapter` declares `date_format` per AD-26, **when** a row's date token is read (e.g. `23/12/2025`), **then** it is parsed as `DD/MM/YYYY` — the year token is present, so no `/CreationDate` reference-date fallback is needed for this product.
4. **Given** `PromericaAdapter`'s dual colones/dólares amount columns in the purchases, other-charges, and voluntary-service sections (structurally identical in shape to BAC credit's, per real extracted text), **when** `AmountColumnRole` is declared for this product, **then** it declares `CURRENCY_VARIANT` — resolved via `normalize_dual_column_amount`, prefer nonzero, prefer CRC if both nonzero (FR-33, AD-28) — the same path Story 4.9 implemented for BAC credit, reusing that resolution function as-is.
5. **Given** the shared `domain/statement_row_extraction.py` date+amount-token classifier (AD-28), **when** a Promerica statement line in the purchases, other-charges, or voluntary-service sections is classified, **then** it is recognized as a data row without a private delimiter check, consistent with Story 4.9's fix.
6. **Given** the CI synthetic fixture gate (mirrors Story 4.9's pattern), **when** a Promerica fixture is generated from the real statement's section titles and row text shape, **then** it replaces the Story 4.5 stub fixture, with goldens updated for all `MUST_PARSE`/`BEST_EFFORT` sections and zero manual edits required.
7. **Given** this story's scope, **when** the Story 4.5 stub adapter still exists in the registry, **then** `PromericaAdapter` (real) supersedes the stub for detection, and the stub module (`adapters/bank/promerica_stub.py`), its tests (`tests/test_promerica_stub_adapter.py`), its fixture generator (`scripts/generate_promerica_stub_fixture.py`), and its fixture PDFs (`tests/fixtures/pdf/promerica_stub_multi.pdf`, `tests/fixtures/pdf/promerica_stub_parse_failure_mixed.pdf`) are removed once `PromericaAdapter` is registered — no dead fake-detection code left reachable.

### Completion Notes List

- **Task 1 decisions applied as coded:**
  - Discrepancy A (payments, 4 amount columns): a payment row's own amount is `amount_tokens[0]` (colones transaction) / `amount_tokens[2]` (US$ transaction), resolved via `normalize_dual_column_amount`. Columns 1/3 (the interest breakdown) are never read. Covered by `test_parse_payment_row_picks_transaction_columns_not_interest_columns`.
  - Discrepancy B (interest, two-line pairing): the parser buffers the most recent non-data line seen while the interest section is active (`pending_interest_concept`) and pairs it with the next amount-only data row; an amount-only row with no buffered concept fails loud via `fail_parse` (`test_parse_interest_amount_only_row_with_no_preceding_concept_fails_loud`).
- **Sign convention (undetermined by PRD, decided here — documented in the adapter module docstring and inline comments):** Promerica encodes negative amounts with a **leading** minus (payments, and an observed purchase refund), unlike BAC credit's trailing-minus convention. The shared `domain.statement_row_extraction` amount pattern only captures a trailing minus, so this adapter extracts signed amount tokens itself (`_AMOUNT_TOKEN_RE`) rather than trusting `extract_row_tokens().amounts` for the final value. `is_data_row()` (sign-agnostic) remains the shared classifier used for row detection, satisfying AC #5's "no private delimiter check." Payment amounts are **not** force-negated (unlike BAC's `_NEGATIVE_LINE_TYPES`) — they already carry the correct sign from the source text.
- **Real gap found during implementation, beyond what Task 1/epic text anticipated:** section **total lines** (e.g. `"Total de compras del periodo de ... 591,158.06 23.00"`) are themselves date+amount shaped and print right after each section's last real row. Without an explicit skip they would be misclassified as a phantom data row under the still-active `MUST_PARSE` section (and, for "Detalle de intereses," as an orphaned amount-only row with no preceding concept, incorrectly triggering the fail-loud path). Added `_TOTAL_LINE_RE` (`^Total\b`) as an early skip in `parse()`'s per-line loop. Covered by `test_parse_ignores_section_and_row_total_lines`.
- **Second real gap: the AC #7-equivalent "unmapped section fails loud" path was unreachable as first coded.** BAC credit's `_is_section_header_line` recognizes unknown sections via a lettered-prefix heuristic (`^[A-Z]\) `) that Promerica's titles don't have (no common prefix). Without an equivalent signal, an unrecognized header-ish line was silently treated as ordinary preamble/boilerplate and never transitioned `SectionCursor` to its "unmapped" state — meaning a row after a truly unrecognized section would have been silently misattributed to whatever the last real section was, rather than failing loud (AD-25/NFR-8). Fixed by explicitly allowlisting Promerica's known non-title boilerplate lines (`_is_known_boilerplate_line`: the payment section's two column sub-header lines, and card-number marker lines via `_CARD_NUMBER_MARKER_RE`) and routing any other unrecognized non-data line — once at least one real section has already started (`seen_section_header`) — through `SectionCursor.see_header_line()`'s own unrecognized-title path, which correctly flips the cursor to "unmapped." Covered by `test_parse_unmapped_section_raises_rather_than_silently_dropping`.
- **Third real gap, found only once `split()` was exercised against a multi-page/reused-metadata PDF path:** the interest section's dateless rows need a reference date, but PDF `/CreationDate` metadata is unreliable once a statement has been through `split()` — `pypdfium2`'s `dst.save(buf)` rewrites a fresh `/CreationDate` (today's date) onto every split chunk, exactly as `BacCreditAdapter`'s own docstring already warns for BAC. Since Promerica has no "Fecha de emisión:"-equivalent printed line documented in the epic text, added `_printed_cutoff_date()` reading the real statement's own printed `"Fecha de Corte DD/MM/YYYY"` line (present in the real-PDF evidence gathered this story) as the primary reference date, falling back to PDF metadata only when that printed line is absent (e.g. a hand-built test PDF with no such line). This is the Promerica-equivalent of BAC's `statement_reference_date()` "prefer printed over metadata" pattern, adapted to Promerica's own field name. Fixture goldens' interest rows use `2026-01-19` (the fixture's printed "Fecha de Corte"), not the fixture's `/CreationDate`.
- **Numeric-month date-format gap (Task 2, anticipated by the story):** extended `domain/statement_dates.py`'s `_SUPPORTED_TOKENS` with `%m` (numeric month) and `%Y` (4-digit year) alongside the existing `%d`/`%b`/`%y`. `PromericaAdapter.date_format = "%d/%m/%Y"`. Added dedicated domain tests (`test_statement_dates_domain.py`) and confirmed the existing `%d-%b-%y`/`%b/%d` formats (BAC credit/debit) are unaffected — full regression pass confirms no behavior change for either.
- **Shared-file collateral found via the Task 4-mandated grep before deleting the stub:** two files outside this story's own module referenced stub artifacts and would have broken on deletion — `scripts/generate_parse_failure_fixture.py` (built `promerica_stub_parse_failure_mixed.pdf` using the stub's pipe-delimited row format) and `tests/test_import_sessions_integration.py` (uploaded that fixture to test the generic "mixed parse failure" import-session behavior, unrelated to `PromericaStubAdapter` itself). Reshaped the generator to emit real Promerica-shaped text (one valid purchase row, one row missing its second amount column) under a new filename `promerica_parse_failure_mixed.pdf`, and repointed the integration test at it — the test's own assertions (evidence kind/shape, `isinstance(amount, str)`) did not hardcode stub-specific values, so no other changes were needed there. `tests/test_parse_evidence.py`'s use of the literal string `"promerica_stub"` as an arbitrary `product_id` value in an unrelated domain test was left as-is (not a reference to the adapter/module being removed).
