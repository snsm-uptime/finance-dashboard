# Story 6.2: Spend by origin for the statement cycle

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the only member of a list,
I want to see how much was spent per origin this statement cycle,
so that I know what went on each card, cash, or unassigned origin.

## Acceptance Criteria

1. **Given** a solo list (`member_count === 1`) with committed purchases in the selected cycle **When** I open list detail **Then** the hero is **period spend by origin** (registered card / Cash / blank) (FR-47). **And** the period is the **statement-cycle** selector from Story 5.9 — same `CyclePeriodSelector` component, same `?period=` query contract, same "All periods" default. **And** included lines follow spend (FR-45 spirit: `purchase` + `classified_purchase_reversal` line types only), not who-owes-whom. **And** amounts are **period spend** (a plain sum of materialized `amount_crc` per origin), not issuer current balance or minimum due.
2. **Given** receipts exist **When** I scroll below the origin cards **Then** the newest-first receipt list remains available unchanged (no gating change to the existing receipts render).
3. **Given** a solo list with no purchases in the selected period **When** I open list detail **Then** the origin-cards hero shows a neutral empty state (no fabricated ₡0 cards, no settle copy).
4. **Given** CI **When** origin totals are computed **Then** domain unit tests cover: single card, multiple cards, Cash, blank (no origin assigned), a mix of all four, a `classified_purchase_reversal` reducing a card's total, and a non-included line type (e.g. `payment`/`fee`) being excluded from every origin's total.

### Review Findings

- [x] [Review][Decision→Patch, resolved] Negative-total origin card has no sign-aware display — `compute_spend_by_origin` sums `amount_crc` **signed** per spec (no `abs()`), so an origin whose only committed activity in the selected period is a `classified_purchase_reversal` (its matching purchase falls outside the resolved `period_start`/`period_end` window) nets to a negative `total_crc`. Decision: show with an explicit sign/label rather than floor-at-zero or leave-as-is. Fixed in `originCardsPropsFrom` (`ui/app/lists/[listId]/page.tsx`) — detects a leading `-` on the raw `total_crc` string (no float parsing) and formats as `-₡N`; `OriginCards` (`ui/components/soft-ledger/OriginCards.tsx`) takes a new `isNegative` flag and applies the existing `text-owe` tone class so it reads as a signal, not a rendering bug. Covered by new tests in `page.originSpend.test.ts` and `soft-ledger.test.tsx`.

Fixed by dropping the redundant `aria-label` — the visible `<h2>` already provides the section's accessible name. Covered by a new test in `soft-ledger.test.tsx`.

## Dev Notes

- **This story is additive only — no existing endpoint's shape changes.** `/expenses` and `/balances` are untouched; a brand-new `/origin-spend` endpoint is added alongside `/cycles`. Do not fold origin totals into `ListBalancesStubResponse` — that response is settle-shaped (pairwise edges) and stays that way for `member_count >= 2` callers.
- **Money math is server-owned, same as everywhere else in this codebase.** Do not sum `amount_crc` strings in the browser with `Number()` — CRC amounts are Decimal-precise strings and this codebase's project-context rule ("Settle math and FX: server-owned — UI displays materialized CRC/originals; never recompute shares/FX in the browser") applies to this aggregation exactly as it does to settle balances. The UI only ever renders `total_crc`/`origins[].total_crc` strings the API already summed with `Decimal`. This is the single most important guardrail for this story — it is the one place a dev agent might reach for a quick `.reduce((a,b) => a + Number(b), 0)` in `page.tsx` instead of a new domain function, and that would be wrong.
- **Reuse Story 5.9's period primitive verbatim — do not build a second one.** The `CyclePeriodSelector` component, its `?period=` URL contract, `resolveSelectedPeriod`, and the API's `resolve_period_bounds`/`resolve_effective_period` are all already period-agnostic (they don't know or care whether the caller is settle or origin-spend). This story's only new period-aware code is Task 2's one-line call to the existing `resolve_effective_period` helper — everything upstream of it (cycle derivation, the picker UI, the default-is-full-history behavior fixed in commit `47d0626`) is unchanged.
- **AD-29 mode switch is already built (Story 6.1) — this story only fills in the solo hero's content.** `showSettleChromeFrom`/the live-`members.length` gate at `page.tsx` already suppresses settle chrome for `member_count === 1`; this story adds what fills that space (origin cards) rather than leaving the neutral "simple" `BalanceStrip` fallback there. Do not touch `showSettleChromeFrom` itself or its shared-mode (`member_count >= 2`) branch — that logic is verified and unchanged.
- **Outstanding Story 6.1 review patches are not this story's problem.** Story 6.1's file has three unresolved `[Review][Patch]` items (a stale-split-state reset in `ManualExpenseForm`, two `ReceiptRow` shrink-effect issues) — none of them touch the files this story modifies (`page.tsx`'s settle-chrome branch, `lists.py`, `spend_by_origin.py`, `OriginCards.tsx`). Do not fix them opportunistically here; they belong to whoever picks up that story's outstanding patches, and mixing them into this diff would make this story's review harder to reason about.
- **Card label resolution has no owner-scoping subtlety here that Story 5.9 had to work around.** `GetListCyclesService`'s label resolution takes "first non-null `origin_card_id` per statement" because a *shared* list's statements can originate from any member's card. A solo list has exactly one member, so every `origin_card_id` on the list belongs to that same person — `get_card_label(card_id)` needs no owner filter (and doesn't have one; see `repositories.py:541`), so this is simpler than the cycles case, not a new problem to solve.
- **Do not gate the new `/origin-spend` endpoint itself on `member_count == 1`.** The API has no concept of "solo mode" today (AD-29's mode switch is a **UI-only** live-membership read, per Story 6.1's dev notes: "no `member_count` field or division-by-member-count logic exists server-side"). The endpoint should compute and return origin totals for *any* list a member can read — the UI decides whether to render `OriginCards` or `BalanceStrip` based on `members.length`, exactly like `showSettleChromeFrom` already does for the settle side. Do not add a member-count check inside `GetListOriginSpendService` — that would be a new server-side coupling AD-29 explicitly avoids ("Mode is live membership count, not a list type" is a UI read, not an API gate).
