# Story 4.6: Upload PDF → detect/split → Import Session

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an authenticated user,
I want to upload a bank-statement PDF and have it staged as an Import Session,
So that multi-statement files are detected and split before I commit anything.

## Acceptance Criteria

1. **Given** I am signed in, **when** I upload a PDF through the web UI (phone or desktop), **then** the file is accepted and stored temporarily on the operator PDF volume with a path reference in Postgres — not in git, **and** non-PDF formats are rejected with a clear error, **and** the path is ephemeral: cleared with the file after successful clean commit (Story 4.9) or when no longer needed for quarantine/review. (FR-13, AD-3)
2. **Given** a valid upload, **when** detect and split run in-process on `api`, **then** an Import Session stages N statements each with product identity, **and** unknown/ambiguous detection fails loudly without silent mis-association. (FR-14, FR-15, AD-4)
3. **Given** a multi-statement PDF, **when** one statement later fails or is skipped, **then** siblings in the same session are not automatically discarded. (FR-15)
4. **Given** review has not committed, **when** I discard the session, **then** only uncommitted session state is dropped — no ledger writes. (AD-4)
5. **Given** a typical single multi-card BAC PDF on the operator's self-hosted hardware, **when** upload → detect/split → review staging completes, **then** the path finishes within an interactive session — review is not an overnight batch job. (NFR-12)

- Real fixtures already committed: `api/tests/fixtures/pdf/bac_credit_synthetic.pdf` (4.4's 3-statement proving fixture), `bac_credit_acceptance_bar.pdf` (4.5's single-statement CI release-gate fixture, exact goldens in `bac_credit_acceptance_bar_goldens.py`), `promerica_stub_multi.pdf`.

**The one consequence that reshapes this story's design:** because real, working adapters are now registered, **uploads can genuinely succeed.** The previous draft's entire premise — "every upload 422s with `unknown_statement_detection` until 4.4 exists, and that's correct" — no longer holds. There is also **no multi-adapter orchestrator to call into** — 4.4 built the *pieces* (`detect_bank_adapter`, one adapter's `.split()`/`.parse()`), not a composed "run the whole pipeline" entry point. That composition — turning one uploaded PDF into a list of per-statement outcomes, including translating a per-chunk `adapter.parse()` exception into a `status="failed"` entry that doesn't take its siblings down (AC #3) — **is the one genuinely new piece of logic this story contributes.** See Task 2 and Dev Notes "The composition this story adds" below.

## Scope Note — what this story does NOT build

- **No new adapter, no changes to `ADAPTERS`, no changes to `CanonicalLine`/`BankAdapter`/`detect_bank_adapter`.** Story 4.4/4.5 own all of that; this story only calls it, for the first time.
- **No bulk/individual review UI, no destination-list assignment** — Stories 4.7/4.8. This story's UI stops at "N statements staged, here's their status" + a Discard action.
- **No commit, no dedup, no ledger writes** — Story 4.9. Nothing in this story writes to `ledger_entries`. `compute_canonical_identity` (already built in 4.4) is not called here.
- **No parse-failure comparison UI or quarantine workflow** — Epic 5. This story only needs to not let one statement's parse failure cascade-discard its siblings (AC #3, structural — the persisted rows and status, not recovery UX).
- **No per-statement PDF splitting-and-storing as separate files on disk.** `adapter.split()` returns in-memory byte chunks for detect/parse purposes; this story persists the *whole uploaded file's* storage path against every statement in the session (all statements share one `pdf_path`). Splitting the stored PDF itself into per-statement files is not required by any AC here and is left for whichever later story needs per-statement source-document display (likely Epic 5's comparison surface). Document this simplification in Completion Notes.

## Dev Notes

### The composition this story adds (read this before Task 2)

Story 4.4's own Completion Notes describe the exact call chain this story is the first to exercise: *"Future caller → `application.bank_adapters.detect_bank_adapter(adapters, override=?, filename=, content_sample=)` → matched `BankAdapter` → `.split(pdf_bytes)` → `list[bytes]` (one per statement) → `.parse(statement_bytes)` per chunk → `list[domain.canonical_line.CanonicalLine]`."* That quote is this story's actual spec for `run_import_pipeline` (Task 2.2) — read it twice. The one thing 4.4 explicitly left undecided, because no caller existed yet, is **what happens when one chunk's `.parse()` raises `InvalidCanonicalLineError` in the middle of a multi-statement file** — 4.4's own adapter contract has no soft-failure return value, it raises. This story's answer, and the only genuinely new design decision here, is: catch that one exception per-chunk, turn it into a `status="failed"` `DetectedStatement` with no rows, and keep going — everything else (detection failure, split failure) still propagates uncaught because there is nothing to stage at all in those cases.

### Completion Notes List

- **Simplification (Scope Note, confirmed as implemented):** `adapter.split()` returns in-memory byte chunks; this story does **not** split-and-store the PDF itself into per-statement files. Every `import_statements` row for one upload shares the same `pdf_path` (the whole uploaded file's storage path). Per-statement source-document display is left for whichever later story needs it (likely Epic 5's comparison surface).
- **Forward note for Story 4.9 (repeated from Story 4.4's own Completion Notes, confirmed still true):** `import_statements.product_id` is `String(64)` holding real adapter ids (`"bac_credit"`, `"promerica_stub"`) — a **different type** than `ledger_entries.product_id` (`UUID`, nullable, Story 3.2's speculative "import stub" column, never wired). Story 4.9, which finally connects staged candidate rows to `ledger_entries`, must make a deliberate schema decision here (migrate `ledger_entries.product_id` to `String`, or map through a lookup) rather than discovering the mismatch mid-implementation.
- **Design decision (the one new piece of logic this story contributes):** `run_import_pipeline` (`api/application/import_session.py`) lets `UnknownBankAdapterError`/`AmbiguousBankAdapterError` (detection) and `InvalidCanonicalLineError` (whole-file split failure) propagate uncaught — nothing to stage in either case — but catches `InvalidCanonicalLineError` **per chunk** around `adapter.parse(chunk)` specifically, turning that one failure into a `DetectedStatement(status="failed", candidate_rows=[])` and continuing the loop. This is deliberate, AC #3-load-bearing behavior: a future change that lets one statement's parse failure abort the whole upload would silently break sibling-survival. Verified via fakes (`test_import_session_application.py`) at both the pure-pipeline level and end-to-end through `UploadStatementPdfService`.
- `UploadStatementPdfService.execute()` deletes the just-saved PDF from storage before re-raising on a rejected upload (unknown/ambiguous adapter, or whole-file split failure) — a rejected upload never leaves an orphaned file on the operator volume (AD-3 spirit). Verified in `test_upload_no_adapter_matches_deletes_saved_file_and_propagates`.
- `DiscardImportSessionService` is idempotent by design: `SqlAlchemyImportSessionRepository.discard_session` only sets `discarded_at` if it is currently `None`; a second discard call on the same session is a no-op that still returns 200, not an error.

## Story-close overview — 4-6-upload-pdf-detect-split-import-session

**Request path:**
Browser → `ui` same-origin BFF (`POST /api/import/sessions`, multipart `FormData` re-post, `forwardCookie`) → `api` (`POST /import/sessions`, `require_authenticated_user`, no alias gate) → `UploadStatementPdfService.execute()`: `validate_pdf_upload` (magic-byte check) → `FilesystemPdfStorage.save()` (whole file to `{PDF_STORAGE_PATH}/{user_id}/{uuid4()}.pdf`) → `run_import_pipeline()` (`detect_bank_adapter` → matched `BankAdapter.split()` → per-chunk `.parse()`, catching `InvalidCanonicalLineError` per chunk only) → `SqlAlchemyImportSessionRepository.create_session()` (one `import_sessions` row + one `import_statements` row per detected statement + one `import_candidate_rows` row per parsed line for staged statements) → `ImportSessionResponse` (counts/status only, no money as JSON numbers). Discard mirrors the same BFF → route → service → repo shape (`DELETE /import/sessions/{id}` → `DiscardImportSessionService` → soft-delete `discarded_at` + best-effort `PdfStorage.delete()` per distinct path).

**Key components:**
`api/domain/import_session.py` (`validate_pdf_upload`, status constants); `api/domain/errors.py` (`UnsupportedFileTypeError`, `ImportSessionNotFoundError`); `api/application/ports.py` (`PdfStorage` Protocol); `api/application/import_session.py` (`run_import_pipeline`, `DetectedStatement`, `ImportSessionRecord`/`StagedStatementRecord`, `ImportSessionRepository` Protocol, `UploadStatementPdfService`, `DiscardImportSessionService`); `api/adapters/storage/pdf_storage.py` (`FilesystemPdfStorage`); `api/adapters/persistence/{migrations/versions/0016_import_sessions.py, models.py, import_sessions.py}` (`ImportSessionModel`/`ImportStatementModel`/`ImportCandidateRowModel`, `SqlAlchemyImportSessionRepository`); `api/api/{deps.py, routes/import_sessions.py, schemas/import_sessions.py, app.py}`; `ui/lib/i18n/upload.ts`; `ui/app/api/import/sessions/{route.ts,[sessionId]/route.ts}`; `ui/app/upload/{page.tsx, UploadPanel.tsx, uploadClient.ts}`.

**Why this shape:**
Mirrors the hex layout precedent Stories 4.1/4.4 already established — pure validation in domain, orchestration/DTOs/Protocols in application, one concrete adapter per driven port (`FilesystemPdfStorage` for the new `PdfStorage` port; `SqlAlchemyImportSessionRepository` for `ImportSessionRepository`). `run_import_pipeline`'s per-chunk-only exception handling is the one genuinely new design decision (see Completion Notes) — everything else in the pipeline (`detect_bank_adapter`, `BankAdapter.split/.parse`) already existed from Story 4.4; this story is the first caller.

**What not to break:**
- `run_import_pipeline`'s per-chunk `InvalidCanonicalLineError` handling is AC #3-load-bearing — a failed statement must never take its siblings down. Detection and whole-file split failures must keep propagating uncaught (nothing to stage).
- `import_statements.product_id` (`String(64)`) is a different type than `ledger_entries.product_id` (`UUID`) — do not silently unify them; Story 4.9 needs a deliberate decision.
- All statements from one upload share one `pdf_path` (whole-file storage, not per-statement splitting-and-storing) — a documented simplification, not an oversight.
- `UploadStatementPdfService` deletes the saved PDF on a rejected upload (unknown/ambiguous adapter, split failure) — don't remove that cleanup when refactoring the service.
- `DiscardImportSessionService`/`SqlAlchemyImportSessionRepository.discard_session` must stay idempotent (second discard is a no-op 200, not an error).
- No commit/dedup/ledger-write path exists yet — `compute_canonical_identity` (Story 4.4) is still uncalled; that wiring belongs to Story 4.9, not this one.
- Upload route/BFF are intentionally **not** alias-gated at the API layer (global entry point) even though the UI page itself still gates on alias — don't add `require_user_alias` to the API route without re-checking Stories 4.7/4.8's list-assignment design.
