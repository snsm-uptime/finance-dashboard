# Story 4.6: Upload PDF → detect/split → Import Session

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an authenticated user,
I want to upload a bank-statement PDF and have it staged as an Import Session,
So that multi-statement files are detected and split before I commit anything.

## Acceptance Criteria

1. **Given** I am signed in, **when** I upload a PDF through the web UI (phone or desktop), **then** the file is accepted and stored temporarily on the operator PDF volume with a path reference in Postgres — not in git, **and** non-PDF formats are rejected with a clear error, **and** the path is ephemeral: cleared with the file after successful clean commit (Story 4.9) or when no longer needed for quarantine/review. (FR-13, AD-3)
2. **Given** a valid upload, **when** detect and split run in-process on `api`, **then** an Import Session stages N statements each with product identity, **and** unknown/ambiguous detection fails loudly without silent mis-association. (FR-14, FR-15, AD-4)
3. **Given** a multi-statement PDF, **when** one statement later fails or is skipped, **then** siblings in the same session are not automatically discarded. (FR-15)
4. **Given** review has not committed, **when** I discard the session, **then** only uncommitted session state is dropped — no ledger writes. (AD-4)
5. **Given** a typical single multi-card BAC PDF on the operator's self-hosted hardware, **when** upload → detect/split → review staging completes, **then** the path finishes within an interactive session — review is not an overnight batch job. (NFR-12)

### The interim adapter-pipeline seam (why this story can still be built now)

The codebase already has precedent for "port exists, real adapter is a deferred stub": `api/api/deps.py#get_bccr_client` returns `UnavailableBccrClient()` with the comment *"BCCR transport is a deferred infrastructure spike"* — FX code is fully built and tested against that port without a real BCCR client existing yet. This story does the same thing for the detect/split pipeline:

- Define an `ImportPipeline` **port** (Protocol) this story's application code calls.
- Provide a trivial **interim adapter** — `NoAdaptersRegisteredPipeline` — that always fails loudly (zero adapters registered yet). This is not a mock or a TODO; it is the objectively correct behavior for "unknown/ambiguous detection" (AC #2, NFR-8) until Story 4.4 registers the first real adapter (BAC).
- Once 4.4 lands and registers a real BAC adapter behind the same `ImportPipeline` port, uploads start succeeding — **without changing any of this story's application/API/UI code.**
- This story's own tests for the "N statements staged" / "sibling not discarded" happy paths use a **fake test-double** implementing `ImportPipeline` (same pattern as `_FakeCardRepo` in `test_cards_application.py`) — they do not need real BAC parsing to exist.

### What this story does NOT build (explicit scope fences)

- **No adapter contract / `CanonicalLine` type definition** — Story 4.4 owns declaring `{bank, product_id, account_kind}` and the detect→split→parse→normalize pipeline internals. This story only defines the narrow *calling* seam (`ImportPipeline.process()`) it needs.
- **No real bank parsing** (BAC or otherwise) — Story 4.4/4.5.
- **No bulk/individual review UI, no destination-list assignment** — Stories 4.7/4.8. This story's UI stops at "N statements staged, here's their status" + a Discard action.
- **No commit, no dedup, no ledger writes** — Story 4.9. Nothing in this story writes to `ledger_entries`.
- **No parse-failure comparison UI or quarantine workflow** — Epic 5 (Stories 5.1–5.3). Per Story 4.9's own AC, "clean parse is the happy path; failures are Epic 5" — this story only needs to not let one statement's detection/parse failure cascade-delete its siblings (AC #3); it does not build recovery UX for that failure.

Story 3.2 added `ledger_entries.product_id` as a speculative `UUID` "import stub" column with an explicit comment that it's "reserved for the future bank-adapter pipeline (product code)." These are two different, currently-unreconciled ideas of what "product_id" means. This story does not touch `ledger_entries` (no commit path exists yet — that's Story 4.9), so it doesn't have to resolve this — but **flag it explicitly in Completion Notes** so whoever implements Story 4.9 (which will finally connect staged candidate rows to `ledger_entries`) sees it and makes a deliberate choice instead of discovering a silent type mismatch mid-implementation.
